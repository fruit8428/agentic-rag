# 模組 3 實施計劃：記錄管理器（Record Manager — 內容雜湊、去重與增量更新）

## 1. 模組目標與學習重點

在**模組 2** 中，我們完成了「樸素導入（Naive Ingestion）」：每次上傳文件時，系統都會無條件新增一筆文件紀錄、把整份文件全部切塊，並把所有分塊送去呼叫 Google Gemini Embedding API。

這在真實生產環境會遇到兩個嚴重問題：
1. **重複導入（Duplicate Ingestion）**：若使用者不小心把同一份 PDF 上傳兩次，資料庫裡會有兩份完全相同的向量分塊（例如 39 + 39 = 78 塊），導致 AI 檢索時被重複的段落塞滿，浪費 Token 又降低準確度。
2. **全量重算浪費（Full Re-indexing Waste）**：當一份 100 頁的文件只修改了其中 1 頁並重新上傳時，樸素導入會把 100 頁全部重新呼叫 Embedding API，既慢又浪費額度。

**模組 3（記錄管理器 Record Manager）的解決方案：**
- **檔案級與分塊級 SHA-256 雜湊（Content Hashing）**：為整份檔案以及切出來的每一個文字分塊（Chunk）計算唯一的 `SHA-256` 指紋。
- **完全重複偵測（Exact Deduplication）**：上傳時若發現完全相同的內容雜湊，0.1 秒內直接識別「內容未變更」，不重複建立文件、不呼叫任何 Embedding API。
- **增量更新（Incremental Indexing）**：當上傳同名但內容有修改的新版檔案時，自動比對新舊分塊的 `SHA-256` 指紋：
  - **未變更的分塊（Unchanged）**：直接保留原向量（**0 次 API 呼叫**），僅更新段落順序 `chunk_index`。
  - **新增/修改的分塊（Added / Modified）**：只針對真正有變動的分塊呼叫 Gemini Embedding API。
  - **已刪除的舊分塊（Removed）**：自動從 `document_chunks` 清除已不存在於新版文件中的舊分塊。

## 3. 驗證步驟

1. **現有文件指紋回填**：為目前已導入的《2026地區年會三全四全頒獎名單》39 個分塊自動補上 SHA-256 指紋（同時保護已手動修正的「林啟平 永久基金*1」段落不被覆蓋）。
2. **重複上傳測試**：再次上傳相同內容的文件，驗證系統在 0.1 秒內回傳「⚡ 內容未變更（已略過重複嵌入）」，且 `document_chunks` 不會產生重複資料。
3. **增量更新測試**：上傳一份測試文件 v1（3 個段落），再上傳修改了其中 1 個段落的 v2，驗證系統「保留 2 個未變動分塊、僅重新嵌入 1 個修改分塊、刪除 1 個舊分塊」，並在前端清楚顯示增量更新報告。
