# 模組 8 實施計劃：子代理（Sub-Agents — 具備隔離上下文的全文件深度分析代理與階層式推理展示）

## 1. 為什麼需要「具備隔離上下文的子代理（Sub-Agents）」？

在前面的模組 1～7 中，我們的主代理（Main Agent）已經擁有：
- **工具 A（`search_knowledge_base`）**：混合檢索 Top-8 段落（適合查特定社團或特定問題）。
- **工具 B（`query_structured_database`）**：Text-to-SQL 結構化筆數統計（適合算總數與篩選明細列）。
- **工具 C（`search_web_fallback`）**：外部即時網路搜尋（適合查即時新聞、天氣與外部資訊）。

然而，當使用者提出 **「全文件深度分析、跨章節總結、整份手冊架構盤點、或某分區/全體獎項綜合比較報告」** 時：
- 若只取 Top-8 段落，會看不見整份文件的全貌（例如漏掉前半部或後半部的獎項種類與集合時間）。
- 若把整份文件（例如 23 頁、51 個分塊、68,013 字）全部塞進 **主對話線程（Main Thread）** 的上下文中，主對話視窗會瞬間塞滿數萬字原始文本，導致後續聊天變慢、Token 暴增，甚至產生「上下文污染（Context Pollution）」。

### 💡 解決方案：主代理委派（Agent Delegation）＋ 隔離上下文子代理（Isolated Context Sub-Agent）

```mermaid
flowchart TD
    U["使用者提出全文件深度分析 / 跨章節綜合報告需求"] --> MAIN["🧠 主代理 (Main Orchestrator Agent)"]
    MAIN -->|檢測到全文件場景\n呼叫 delegate_to_document_subagent| SUB["🤖 全文件深度分析子代理 (Isolated Sub-Agent)\n【擁有獨立隔離上下文，不污染主對話記憶】"]
    subgraph ISOLATED["🔒 子代理隔離上下文空間 (Isolated Context Window)"]
        SUB --> ST1["嵌套工具 1：subtool_inspect_document\n(讀取文件元數據與章節範圍)"]
        ST1 --> ST2["嵌套工具 2：subtool_scan_all_chunks\n(全文件分段掃描與結構化提取)"]
        ST2 --> ST3["嵌套工具 3：subtool_synthesize_report\n(子代理獨立推理與深度彙整)"]
    end
    ST3 -->|僅回傳高密度結構化精華報告\n(節省 90%+ 主對話上下文)| MAIN
    MAIN --> UI["🖥️ 前端階層式推理樹 (Hierarchical Agent Trace UI)\n展示主代理委派邏輯 + 子代理嵌套工具步驟 + 最終報告"]
```

## 2. 後端架構設計（`backend/app/services/subagent.py`）

1. **子代理推理與報告結構（Pydantic `SubAgentAnalysisSchema`）**：
   - `main_agent_delegation_reason`：主代理為何將此任務委派給子代理的推理說明。
   - `subagent_reasoning_steps`：子代理在隔離上下文中的逐步推理過程。
   - `nested_tool_calls`：子代理內部執行的嵌套工具調用清單（含工具名稱、輸入參數、執行結果摘要與耗時/掃描量）。
   - `context_saving_stats`：隔離上下文掃描總字數 vs. 回傳主代理精華字數（計算上下文壓縮率與節省百分比）。
   - `synthesized_report`：子代理產出的結構化深度分析報告。

2. **主代理第四大工具：`delegate_to_document_subagent`（於 `backend/app/routers/chat.py` 註冊）**：
   - 當使用者詢問：
     - 「全文件總結 / 整份文件有哪些獎項與頒獎時段流程？」
     - 「請派子代理深度分析第四分區（04-1～04-7）所有扶輪社的得獎分布與集合動線」
     - 「比較整份名單中第三全會與第四全會的所有獎項差異」
   - 主代理自動呼叫 `delegate_to_document_subagent(task_description, focus_scope)`，並透過 SSE 即時向前端推送子代理的每個嵌套工具步驟（`subagent_progress` 事件）。
